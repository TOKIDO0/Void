# VOID 下一步开发主文档

> 文档作用：作为当前阶段唯一的“下一步开发”主文档，只负责定义当前主线目标、边界、优先级和阶段结论。  
> 使用方式：新开窗口继续开发时，先读本文档，再按本文档指向去读对应专项文档。  
> 文档边界：本文档不再承担历史补充记录、完整进度日志、提示词模板或执行细项验收表，这些内容应放到各自独立文档。

## 1. 当前阶段定位

当前仍处于 Web MVP 阶段。

本阶段主线不是记忆系统、语音系统或桌面端，而是把“文本模型体验”稳定到可继续扩展的程度。

当前阶段只允许推进：
- 模型配置与多 Provider 文本链路
- 中转站 / 官方 API / OpenAI-compatible 链路稳定性
- 主界面克制回复预览
- 展开面板长文本阅读体验
- 当前会话本地持久化
- 模型错误提示可读化

当前阶段不要推进：
- 长期记忆系统
- 健康档案
- 完整 STT / TTS
- 主动监听唤醒
- 电脑控制
- Tauri 打包
- 手机端适配

## 2. 下一步唯一任务目标

下一步任务确定为：

**完成 Web MVP 的文本模型体验稳定化收尾，并把真实模型链路稳定性纳入同一轮主线。**

这一步的核心不是继续堆功能，而是把当前已经做出来的文本链路变成真正可持续开发的稳定底座。

## 3. 下一步任务拆分优先级

### 3.1 第一优先级：真实模型链路稳定化

目标：
- 修正开发代理、中转站、官方 API、OpenAI-compatible 链路中的实际请求问题。
- 确保用户填写正确的 `Base URL`、`API Key`、模型名后，请求可以真正发到目标模型服务，而不是先死在本地代理层。
- 确保错误信息能明确指出是代理不可用、鉴权失败、模型名错误、限流还是服务端异常。

当前已知必须覆盖：
- `/void-model-proxy` 在开发环境不可用时的回退逻辑。
- 中转站场景下修改 `Base URL` 后，仍能保留原本所选厂商的模型列表。
- OpenAI-compatible endpoint 规范化，避免重复拼接路径。

### 3.2 第二优先级：流式回复与回复展示稳定化

目标：
- 流式回复开启后，主界面预览层和展开面板都能实时看到增量内容。
- 流式过程中不要因为 React key 或动画依赖写法导致闪烁、重挂载、空白块或抖动。
- 非流式请求保持现有完整回复体验。

### 3.3 第三优先级：长文本承载检查

目标：
- 长输入不撑坏底部输入框布局。
- 主界面回复层继续保持“预览层”角色，不变成聊天记录页。
- 展开面板能承担长文本阅读。

### 3.4 第四优先级：当前会话本地持久化收尾

目标：
- 刷新页面后当前会话可恢复。
- 恢复出来的历史不会把下一次模型请求上下文撑爆。
- 本地会话历史和真正发送给模型的上下文长度必须分离控制。

### 3.5 第五优先级：模型配置面板继续收敛

目标：
- 自定义模型名继续保留，但只作为高级入口。
- 用户修改 `Base URL` 后，不得丢失已经选中的厂商模型系列。
- 预设、Provider、Base URL、模型下拉之间的关系要清晰、稳定、可预期。

## 4. 当前阶段完成标准

当下面条件同时成立时，这一阶段可以认为完成：

1. 中转站、官方 API、OpenAI-compatible 场景下，正确配置后可以稳定请求。
2. 常见错误都有可读提示，不再只给浏览器层模糊报错。
3. 主界面和展开面板都能稳定承载流式或非流式长回复。
4. 刷新后当前会话可恢复，但恢复不会破坏后续请求。
5. 模型配置面板不会因为修改 `Base URL` 就丢失原有模型系列选择。
