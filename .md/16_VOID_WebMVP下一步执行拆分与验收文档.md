## 1.1 当前轮开发决策锁定

本轮执行过程中，下面这些产品决策直接视为已确认，不再在写代码阶段反复改定义：

1. “思考模式”已完成：
   - 独立开关已接入
   - 请求参数与策略切换已接入
   - agent 流体确认特效已接入
2. 文件上传第一阶段已完成文本类闭环：
   - 已支持文本类选择、拖拽、发送、取消和持久化
   - 图片等非文本文件支持后续再做
3. 语音第一闭环必须走服务端第三方语音 API，不使用浏览器原生 STT / TTS 作为正式方案。
4. 语音厂商允许双供应商并行接入，但必须明确主次：
   - 主链路优先一个正式供应商
   - 第二供应商用于补足音色、角色感或特定模式
   - 不允许让前端直接暴露两套混乱配置
5. 人格与安全边界这一轮先做验证方案和记录输出，不在本轮默认直接修改 prompt。

## 1.2 正式开发前必须先确认的工程前置项

在开始写代码前，先确认下面几项是否齐备。若未齐备，优先补充文档或占位配置，不直接写半套实现：

1. 语音服务端第三方 API 的接入对象是否已选定。
2. 若采用双供应商方案，是否已经明确：
   - 主供应商负责什么
   - 次供应商负责什么
   - 前端如何暴露音色选择而不让设置面板失控
3. 当前正式模型代理链路是否允许继续扩展语音代理接口。
4. 语音监听开关是否进入本地持久化，以及重开应用后是否恢复关闭。
5. TTS 音色策略是否固定为：
   - 日常对话默认音色
   - 特定模式可切换音色
   - 不允许自动乱切换破坏人格一致性

## 3. 任务 1：语音第一闭环

### 3.1 目标

- 默认关闭监听
- 接入 STT
- 接入 TTS
- 让 `speaking` 状态与真实 TTS 输出绑定
- 语音链路以服务端第三方语音 API 为正式方案
- 先锁定最适合 VOID 的语音供应商主次方案

### 3.2 实施步骤

1. 先锁定语音供应商方案，不在接口未定时写猜测性代码。
2. 语音供应商优先按“主供应商 + 次供应商”的结构思考：
   - 主供应商承担 STT、实时交互、默认 TTS 主链路
   - 次供应商可用于补足音色库、角色化语音或特定模式
   - Web MVP 阶段先控制前端复杂度，不开放过多乱序选择
3. 若最终采用火山方舟 + MiniMax 双接入，建议优先结构为：
   - 火山方舟：STT、实时交互、默认中文 TTS 主链路
   - MiniMax：补充高质量角色音色、讲故事模式、特殊声线模式
4. 先完成监听开关默认关闭，保证刷新、重启和新开页面都不会自动常开监听。
5. 梳理麦克风授权、音量检测、输入区、对话发送之间的现有关系，避免新接 STT 时把当前状态机打乱。
6. 当前 MVP 语音方案锁定为服务端第三方 API，不使用浏览器原生 STT / TTS 作为正式实现。
7. 先决定 STT 最小闭环是：
   - 实时识别
   - 还是结束录音后转写
   本轮优先选最稳定、最小改动的一种，不追求一步到位做全双工。
8. 让语音输入最终落到与文本输入相同的发送入口，避免形成第二套消息主链路。
9. 为 TTS 设计独立适配层，把 `speaking` 状态与真实播放时长、音频元素状态或播放事件绑定，不再用纯定时器模拟。
10. 将 TTS 音色策略明确拆成两层：
    - 默认人格音色：长期稳定，不轻易切换
    - 场景音色：如讲故事、特殊陪伴模式、角色化内容
    不允许为了“好玩”在日常主对话里频繁换声，破坏 VOID 的人格连续性。
11. 如果需要服务端代理二进制音频流或语音文件，先补清楚代理接口边界、鉴权方式和错误映射。
12. 补齐中断策略：用户打断、播放失败、识别失败、权限拒绝、接口超时、音频解码失败时状态如何回收。
13. 检查展开层、回复层、Blob 状态和语音流程之间是否会出现冲突状态。
14. 保证“默认关闭监听”高于一切现有便利逻辑，已授权麦克风也不能在页面加载后自动进入监听。
15. 在正式实现前先输出一份语音供应商决策：
    - 是否双接入
    - 谁做主链路
    - 谁做补充音色
    - Doubao 具体选哪些能力
    - MiniMax 是否只用于 TTS

### 3.3 涉及文件

- `src/features/voice` 相关文件
- `src/features/void-stage/VoidStage.tsx`
- `src/features/text-entry` 相关文件
- 视实现决定是否新增 STT / TTS provider 适配文件
- 视实现决定是否补充服务端语音代理相关文件

### 3.4 产出要求

- 监听默认关闭且状态清晰
- 语音输入走入统一消息主链路
- `speaking` 与真实 TTS 行为绑定
- STT / TTS 与第三方服务的失败路径清晰可回收
- 有明确语音供应商主次方案，而不是边写边试

### 3.5 验收方法

- 页面初始进入时监听为关闭状态
- 用户授权后可完成一次语音输入并触发真实发送
- 模型回复可触发真实语音播放
- 播放期间 `speaking` 状态正确，播放结束后正确回收
- 已有麦克风权限时刷新页面，也不会自动开始监听
- 若采用双供应商方案，前端不会出现混乱的配置暴露

## 4. 任务 2：人格与安全边界验证

### 4.1 目标

- 验证 VOID 人格是否稳定
- 验证善意谎言边界是否符合设计
- 验证自伤、伤害他人、医疗、法律、财经等高风险边界

### 4.2 实施步骤

1. 先以 `11_VOID_人格与安全边界测试用例.md` 为主清单，不重新发散生成新的无边界测试范围。
2. 把测试分成 3 组：
   - 情绪稳定性
   - 善意谎言边界
   - 高风险安全边界
3. 对每一组记录：
   - 实际输出是否符合预期
   - 是否出现角色漂移
   - 是否出现风险越界
4. 如果发现问题，优先判断是：
   - system prompt 不足
   - 前端提示不明确
   - provider 行为差异
5. 将“需要修 prompt”“需要修产品限制”“需要加额外防线”的问题分开记录，避免混成一个泛泛结论。
6. 输出一轮可执行修正结论，为下一轮人格和安全收敛做输入。
7. 本轮默认只输出验证结论和修正入口，不自动直接修改 prompt，除非后续单独确认。

### 4.3 涉及文件

- `03_VOID_System_Prompt正式版.md`
- `11_VOID_人格与安全边界测试用例.md`
- 视验证结果决定是否回改 prompt 接入或错误提示相关代码

### 4.4 产出要求

- 有明确验证结果，而不是只说“基本正常”
- 有明确问题分类
- 有明确下一轮修正入口

### 4.5 验收方法

- 情绪回应稳定性有结论
- 善意谎言边界有结论
- 高风险边界有结论
- 每类问题都能指出后续应修哪一层
