# VOID 回复展开动效与模型接入配置方案

> 本文档用于对齐下一步实现方案。当前只做设计确认，不直接写实现代码。

## 1. 先解释两个模型参数

### 1.1 温度

“温度”对应模型请求里的 `temperature`。

它控制回复的随机性和发散程度：
- 数值低，例如 `0.2`：回复更稳定、更保守、更像按规则输出。
- 中间值，例如 `0.7`：更自然，有一定变化，适合日常对话。
- 数值高，例如 `1.2` 以上：更发散、更有创意，但也更容易跑偏。

VOID 当前默认 `0.7` 是合理的，因为它不是严格代码助手，而是情绪型私人 Agent，需要自然一点，但不能太飘。

建议：
- 普通聊天：`0.6 - 0.8`
- 严肃问题、技术问题、健康/法律/财经边界问题：`0.2 - 0.5`
- 创意写作、灵感发散：`0.8 - 1.2`

### 1.2 最大输出

“最大输出”对应模型请求里的 `max_tokens`。

它不是严格的“最大中文字数”，而是最大 token 数。token 可以理解为模型处理文本的最小片段。中文里通常 1 个汉字可能接近 1 个 token，但不同模型和服务商会有差异。

它确实会影响 AI 回复的最长长度：
- 数值太小：回复可能被截断。
- 数值适中：回复完整但不会太啰嗦。
- 数值太大：模型可以输出更长内容，但会更慢，也可能更费额度。

当前默认 `1200` 适合 VOID 的 MVP 对话。如果后续要让 VOID 输出长文档、长分析，再单独做“长回复模式”，不要把默认值调得过高。

## 2. 浏览器直连为什么会失败

你看到的核心错误是：

```text
No 'Access-Control-Allow-Origin' header is present on the requested resource.
```

这说明目标模型服务没有允许浏览器从 `http://localhost:5173` 这个页面直接请求它。

这不是 VOID 前端简单改几行 `fetch` 就能解决的问题。CORS 是浏览器安全机制，是否允许跨域由目标 API 服务响应头决定。目标服务不加允许头，浏览器就会拦截。

所以现在结果是正常的：
- `development-proxy` 可以成功：因为请求先发给本地 Vite 代理，再由本地 Node 服务转发给模型服务，绕过浏览器 CORS。
- `direct` 失败：因为浏览器直接请求第三方模型 API，对方没有允许这个网页 origin。

另外日志里的：

```text
api.openai.com/v1/chat/completions 401
```

这是 OpenAI 官方接口返回的鉴权失败，通常是 API Key 错误、为空、过期，或账号无对应权限。它和 FreeModel 的 CORS 是两个问题。

## 3. 关于非官方 API / 自定义服务的配置方式

产品里不要把入口写成“中转站教程”，更合适的叫法是：

- OpenAI-compatible 服务
- 自定义模型服务
- 第三方兼容 API
- 自定义 Base URL

用户配置方式应该是：

1. Provider 选择 `OpenAI-compatible`。
2. Base URL 填服务商给的 API 根地址，例如：
   ```text
   https://example.com/v1
   ```
3. Model Name 填服务商提供的模型名。
4. API Key 填该服务商提供的密钥。
5. 请求方式优先选择 `开发代理`。
6. 直接删除“浏览器直连”不行吗？毕竟这个东西那么多弊端，好像没有什么作用啊？毕竟我们的这款agent是去中心化，本地的agent，就不需要浏览器直连？你觉得呢？你怎么看？

需要明确告诉用户：
- 大多数模型 API 不支持浏览器直连。
- 浏览器直连会暴露 API Key，不适合作为正式生产方案。
- 生产 Web 或 Tauri 版本必须走正式代理或本地安全通道。



## 4. 正式代理方向

MVP 当前只有 Vite 开发代理，它只适合本地开发。

后续正式方案建议分两类：

### 4.1 Web 生产版

需要一个服务端代理：
- 前端只请求 VOID 自己的 `/api/model/chat`。
- API Key 不直接暴露给浏览器请求第三方服务。
- 服务端根据用户配置转发到 OpenAI-compatible / Anthropic 等 provider。
- 服务端返回统一错误结构。

### 4.2 Tauri 桌面版

更适合走本地代理：
- 前端调用 Tauri command。
- Tauri Rust 层或本地 sidecar 负责请求第三方模型 API。
- API Key 存在本机安全存储或本地配置中。
- 浏览器 WebView 不直接请求第三方模型服务。

结论：浏览器直连只能作为调试选项，不应该作为正式主线。

## 5. 当前聊天记录窗口的问题

现在的 `ConversationHistoryOverlay` 是普通覆盖层，能用，但不符合 VOID 的视觉定位。

问题：
- 它像普通工具弹窗，不像 VOID 主界面的一部分。
- 对话展示方式接近普通聊天 App。
- 打开方式和当前回复层之间没有视觉连续性。
- 没有使用 R3F / GLSL 光效承接主视觉。

所以后续应删除或替换当前普通历史弹窗，不在主体验里保留这个草率版本。

## 6. 新方案：从 AI 回复框展开长回复模态

目标：保持当前 AI 回复框的样子和回复形式不变。只有当用户点击当前回复框时，才触发展开动画，进入长回复 / 当前会话查看模式。

### 6.1 触发方式

建议：
- 当最近一条回复存在时，回复层可点击。
- 短回复点击后也可以打开详情，但视觉上主要服务长回复。
- 如果当前处于 `thinking` 或 `error`，不触发展开。
- 用户按 `Escape` 或点击暗区关闭。

### 6.2 动画导演思路

动画顺序建议：

```text
用户点击回复框
  -> 回复框下方能量线增强
  -> 一束竖向 beam 从回复框中心向上下延展，就像是出现一个裂缝（裂缝并不是一条直线，而是不规则的裂缝，裂隙当中有辉光溢出的效果）
  -> beam 中心出现裂开效果
  -> 裂缝两侧产生微弱粒子和边缘辉光
  -> 模态内容从裂缝中显现
  -> 对话内容逐行淡入
```

关闭时反向：

```text
内容淡出
  -> 模态向中心收束
  -> beam 合拢
  -> 回复框恢复原来的克制状态
```

### 6.3 技术分工

R3F / GLSL 负责：
- 竖向 beam。
- 中间裂开光缝。
- 能量线扩散。
- 光雾、粒子、扫描线、边缘辉光。

GSAP 负责：
- DOM 模态透明度、位移、缩放。
- 动画时间线编排。
- 打开/关闭状态衔接。
- 响应式和 reduced motion 处理。

CSS 只负责布局、字体、基础定位，不负责主光效。

## 7. 可选光效清单

以下效果可以组合，但不要一次全上，否则会过度。

### 7.1 推荐默认组合

1. 竖向 beam 【选这个】
   - 一条从回复框中心升起的细长能量柱。
   - 用 GLSL 控制中心亮度和边缘羽化。

2. 中央裂缝 【选这个】
   - beam 中部左右分开，像空间被打开。
   - 裂缝边缘有高亮 Fresnel 感。

3. 横向能量涟漪 【选这个】
   - 从点击点向两侧扩散。
   - 呼应现有 EchoLightLine。

4. 微粒上浮
   - 少量粒子从裂缝边缘向上漂移。
   - 必须克制，不能变成粒子雨。

5. 内容显影扫描
   - 模态里的文本不是突然出现，而是从中间到上下轻微显影。

### 7.2 可以后续增强的效果

1. 光线折射 【选这个】
   - 裂缝附近产生轻微折射扰动。
   - 适合用 shader 做噪声位移。

2. 色散边缘 【选这个】
   - 极轻微青蓝边缘分离。
   - 不能做成赛博朋克彩虹。

3. 呼吸式边框 【选这个】
   - 模态边缘不是实线框，而是若隐若现的能量边。

4. 深度雾层
   - 模态背后有很薄的光雾，制造纵深。

5. 关闭时能量回收 【选这个】
   - 内容消失后，光线向回复框下方能量线收回。

## 8. 对话内容样式

不使用普通聊天 App 的圆角气泡。

建议样式：
- 用户消息靠右，VOID 消息靠左。
- 每条消息没有实心气泡背景。
- 文本块只有两个角标：
  - 左上角短线角标。
  - 右下角短线角标。
- 角标用细光线，不用 CSS box-shadow 主效果。
- 每条消息之间留足呼吸感。
- 长文本支持滚动，但滚动区域要克制，不做大面积聊天窗口。

视觉关键词：
- 低亮度。
- 悬浮。
- 精密定位感。
- 非普通聊天 App。
- 像从 VOID 的回复光线里展开的信息层。

## 10. 实现约束

- 不使用 CSS 或 SVG 承担主光效。
- 主光效必须用 R3F / GLSL。
- GSAP 使用 timeline 编排，不用一堆散乱 delay。
- R3F `useFrame` 里不调用 React `setState`。
- Canvas 固定在容器里，避免重排。
- 动画需要支持移动端尺寸。
- 需要考虑 `prefers-reduced-motion`，减少动画但不破坏可用性。
- 不做完整聊天列表，不做历史持久化。
- 不接记忆、健康档案、STT/TTS。

## 11. 需要确认的问题

实现前需要你确认：

1. 点击回复框后，展开内容是只显示“最近一条完整回复”，还是显示“当前会话内的多轮对话”？
2. 如果显示多轮对话，是否只显示最近 6-10 条，避免变成传统聊天列表？
3. 用户消息和 VOID 消息是否都进入展开模态，还是只展示 VOID 的长回复？
4. 打开动画的速度你想要哪种？
   - 慢：更电影感，约 `1.2s - 1.6s`
   - 中：更顺手，约 `0.8s - 1.1s`
   - 快：更工具化，约 `0.45s - 0.7s`
5. 默认光效组合是否采用：
   - 竖向 beam
   - 中央裂缝
   - 横向能量涟漪
   - 少量微粒
   - 内容显影扫描
6. 当前左端 agent 操作栏里的 `History` 入口要不要保留？
   - 方案 A：保留，但点击后也走同一个电影式展开。
   - 方案 B：移除，只允许从回复框点击展开。
7. 展开模态里的标题是否显示？
   - 方案 A：不显示标题，保持沉浸。
   - 方案 B：显示极小的 `Session` / `VOID` 标识。

## 12. 建议默认答案

我对上面问题的回答：

1. 当前会话内的多轮对话（所有该窗口之前的对话都要显示）
2. 都显示，毕竟有些时候用户会需要用到之前的一些信息
3. 用户和void的都进入展开模态
4. 动画速度选择中档，约 `0.95s`。
5. 我已经在每一项要加入的功能后面加了一句 【选这个】 只要有这个的就加入，没有的就不要加了
6. `History` 入口保留，点击后复用同一个展开动画。
7. 展开模态不显示大标题，只保留极小的 `Session` 标识。
