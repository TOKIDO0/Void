# VOID 产品定位与边界文档

> 文档作用：定义 VOID 的产品方向、第一阶段边界、禁止漂移方向。  
> 适用对象：产品规划、架构设计、后续 Codex / Claude 开发任务。

## 1. 产品一句话定义

VOID 是一款本地运行、本地存储、可接入用户自定义云端大模型 API 的情绪型私人 Agent。它不是普通聊天工具，而是一个能理解用户情绪、长期学习用户习惯、分区记忆重要信息，并以低沉、克制、温柔方式陪伴用户的个人伴侣和管家。

VOID 的 MVP 必须支持长文本输入和长文本输出，但长文本能力是基础能力，不是产品定位本身。它可以处理文章、代码、总结、分析和档案整理，但这些能力都应该服务于“情绪型私人 Agent”这个核心方向，而不是把产品做成通用写作工具、代码 IDE 或纯生产力大模型壳。

## 2. 产品核心特征

- 情绪感知：理解用户语气、文本、上下文和近期情绪走势。
- 语音优先：最终形态主要交互方式是语音聊天，文字输入作为补充；但在当前 Web MVP 阶段，文本链路要先稳定。
- 电脑端优先：VOID 的正式产品形态是可安装到电脑上的本地 Agent，不做手机端 App；当前 Web 形态只是 MVP 开发和验证载体。
- 本地数据主权：对话、记忆、健康档案和用户偏好默认存储在用户本地。
- 云端模型调用：LLM 使用用户配置的模型 API，不要求用户本地部署大模型。
- 可扩展模型适配：支持 OpenAI、Anthropic、MiniMax、DeepSeek、Ollama、智谱等主流模型，以及 OpenAI-compatible 中转站。
- 分块记忆：不同类型的信息进入不同记忆区，按需召回，避免混淆。
- 个人管家：能记录事项、整理需求、提醒用户、建立健康档案。
- 极简前端：黑色背景，只有中央发光 Blob 主体和底部胶囊输入区。
- 长文本承载：输入、回复、历史面板都必须能够承载较长内容，历史面板负责阅读长回复，主界面只保留克制预览。

## 3. 第一阶段主线

第一阶段只做 Web MVP。

这里的 Web MVP 只代表当前阶段的开发形态，不代表 VOID 最终要做成网页产品。VOID 的正式方向是电脑端可安装应用，后续可以通过 Tauri 等桌面容器承载当前 Web 前端、GSAP 动效和 R3F 动效。手机端 App 当前不进入产品路线，避免为了小屏适配和移动端交互牺牲主要开发效率。

目标是先验证：
- 视觉气质是否成立。
- GSAP 动效是否流畅。
- idle / listening / thinking / speaking 状态机是否自然。
- 文本对话人格是否符合 VOID。
- 模型 API 配置是否足够灵活。

第一阶段不直接做：
- Tauri 桌面打包。
- 手机端 App。
- 完整本地大模型部署。
- 复杂插件系统。
- 控制电脑文件或系统设置。
- 把 VOID 定位成 Claude / Codex 那种以通用生产力为中心的模型壳。
- 把 VOID 做成只能短聊的情绪陪伴机器人。

## 4. 关于“去中心化”的准确解释

VOID 的去中心化不是指所有模型都在本地运行，而是指：

- 用户数据默认只在本地设备保存。
- 用户自己配置模型服务。
- 用户可以选择官方 API、中转 API、本地 Ollama 或未来其他模型服务。
- VOID 不依赖一个统一中心服务器保存用户资料。

因此，VOID 可以调用云端模型 API，但不能把用户长期记忆、健康档案和私人资料上传到 VOID 自己的中心数据库。

## 5. 产品非目标

VOID 不是：
- 医生、心理咨询师、律师或投资顾问。
- 单纯的 ChatGPT 外壳。
- 只靠拟人文案伪装的普通助手。
- 满屏按钮和复杂菜单的工具型软件。
- 默认收集用户数据的云端 SaaS。

## 6. 模块化开发原则

所有开发必须模块化，原因是 VOID 后续会长期扩展记忆、语音、模型、健康、前端动画和本地存储能力。如果早期把逻辑写成一团，后期定位 bug、替换模型、删除功能都会非常困难。

建议模块边界：

- `ui`：页面、布局、组件、视觉状态。
- `animation`：GSAP timeline、动效状态机、声波渲染。
- `agent-core`：对话流程、人格调用、工具调度。
- `model-providers`：OpenAI、Anthropic、DeepSeek、MiniMax、Ollama 等模型适配器。
- `memory`：分区记忆、召回、写入、删除。
- `health-profile`：健康档案、人物区分、敏感信息治理。
- `voice`：STT、TTS、麦克风权限、音频流。
- `wake`：唤醒词、判断唤醒、无效语音过滤。
- `settings`：用户配置、API Key、本地隐私开关。

## 7. 关于长文本能力的边界

VOID 必须支持长文本，但不应把“长文本输出”当作唯一卖点。

推荐理解方式：

- 情绪陪伴场景：默认短句、克制、自然。
- 复杂说明场景：允许更完整的解释和结构化内容。
- 长文 / 代码 / 档案整理场景：允许长输出，但应由用户意图驱动，不应每次都默认拉满。

因此，VOID 既不能被限制成只会短聊，也不能被误做成通用写作平台。

## 8. 必须避免的产品漂移

- 不要把 VOID 做成普通后台管理系统。
- 不要为了功能堆叠牺牲极简主界面。
- 不要把所有记忆混在一个总表或一个 prompt 里。
- 不要默认开启长期监听。
- 不要把健康档案做成医疗诊断系统。
- 不要为了兼容所有模型而写大量猜测性兜底代码；模型适配应通过清晰 provider contract 实现。
